# Configuration

embry0 uses environment variables for infrastructure config and API endpoints for runtime config.

## Environment variables (`.env`)

| Variable | Default | Description |
|----------|---------|-------------|
| `DEFAULT_AUTH_MODE` | `oauth` | How agents authenticate to Anthropic: `oauth` (a Claude subscription token) or `api_key`. A repo, job or agent can override it; see [Agent execution & auth modes](#agent-execution--auth-modes) |
| `ANTHROPIC_API_KEY` | — | API key, for `DEFAULT_AUTH_MODE=api_key`. Served to jobs when no [credential registry](credentials.md) account is usable |
| `CLAUDE_CODE_OAUTH_TOKEN` | — | OAuth token, for the default `DEFAULT_AUTH_MODE=oauth`; generate with `claude setup-token` |
| `AGENT_MODEL_PROVIDER_CHECK` | `false` | Refuse to save an agent definition (`POST /agents`, `PUT /agents/{type}`, the MCP `agent_update` tool) whose model routes to a provider with no credential configured, or to no catalogue provider at all, with a 422 that names the provider. Off, the save succeeds and the job fails when it runs. `GET /agents` reports `provider` and `provider_ready` per agent either way; see [provider readiness](providers.md#provider-readiness) |
| `OPENAI_COMPATIBLE_PROVIDERS` | — | The OpenAI-compatible providers this deployment offers, comma-separated: `openai`, `openrouter`, `google`, `groq`, `deepseek`, `custom`. Unset offers none, and every model routes as before; see [OpenAI-compatible providers](providers.md#openai-compatible-providers) |
| `OPENROUTER_CATALOG_REFRESH_HOURS` | `24` | Hours between reads of [OpenRouter's live model list](providers.md#openrouters-live-model-list) while `openrouter` is enabled; `0` reads it only on demand (the OpenRouter card's **Read the list now**) |
| `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `DEEPSEEK_API_KEY`, `CUSTOM_LLM_API_KEY` | — | An enabled OpenAI-compatible provider's API key, served to jobs when no [credential registry](credentials.md) account is usable. `CUSTOM_LLM_API_KEY` counts only with `CUSTOM_LLM_BASE_URL` |
| `CUSTOM_LLM_BASE_URL` | — | The custom provider's OpenAI-compatible API root for that env key, e.g. `http://10.0.0.5:11434/v1` |
| `LOCAL_LLM_UPSTREAM` | (empty) | The API root of the operator's own model server (`http://host:port/v1`). Set, the orchestrator starts the `local-llm-proxy`, and every sandbox run on the custom provider reaches the server through it, with no egress exception for the server's machine ([Local models](providers.md#local-models), [ADR 0023](adr/0023-local-llm-proxy.md)). Calls the orchestrator makes itself (briefs, the Slop-O-Meter's judgments) still use the custom account's base URL |
| `LOCAL_LLM_API_KEY` | (empty) | The key the model server checks, added by the proxy and never in a sandbox; empty sends none |
| `LOCAL_LLM_MAX_REQUEST_BYTES` | `8388608` | The largest request the local-llm-proxy forwards; over it the proxy answers 413 |
| `LOCAL_LLM_CONTEXT_TOKENS` | `0` | The context window of every `custom/` model, in tokens, overriding what the server's `/models` reports; `0` reads `/models` |
| `LOCAL_LLM_SLOT_WAIT_SECONDS` | `900` | How long a run that has to use the local model waits for one of its slots (`local_max_runs` in the provider settings) before the job is parked for five minutes ([Spent account waits](providers.md#spent-account-waits)) |
| `MODEL_PROXY_MAX_REQUEST_BYTES` | `33554432` | The largest model request the xai-proxy and auth-proxy forward. Every agent turn resends the whole conversation; over the cap the proxy answers 413 and the run ends as `ERR_CONTEXT_WINDOW_EXCEEDED` |
| `GITHUB_TOKEN` | — | GitHub personal access token |
| `GITHUB_WEBHOOK_SECRET` | — | HMAC secret for webhook verification |
| `WEBHOOK_NOTIFY_URL` / `WEBHOOK_NOTIFY_SECRET` | empty | Where embry0 POSTs its own events (`job.<status>`, `watcher.proposed`, `agent.question`) and the secret it signs them with ([outbound notifications](webhooks.md#outbound-notifications)). A fallback for the dashboard's integration settings: a value saved there wins |
| `WEBHOOK_PUBLIC_URL` | empty | The public base URL forges deliver webhooks to, with no path, e.g. `https://webhooks.example.com` (a webhooks tunnel hostname, not the dashboard's). It is the install target of an organization webhook and of the organization `hook` action (`<WEBHOOK_PUBLIC_URL>/api/v1/webhook`), and the only origin organization discovery counts as pointing here: a repository's hook points here only when its URL starts with it. `DASHBOARD_PUBLIC_URL` and `SSO_PUBLIC_ORIGIN` are not webhook origins (the public dashboard answers 404 on webhook paths). Unset or a loopback address, organization webhooks cannot be installed, the `hook` action is skipped, and a repository's hooks are unknown rather than absent, and the needs list asks for this setting. See [webhooks](webhooks.md#organization-webhooks-github) |
| `AUTH_DEV_MODE` | `false` | Turn API authentication off (HTTP, admin gate, WebSocket, SSE). The only setting that allows an empty `API_KEY`. For a local-only instance; startup refuses it when SSO is configured or the root `.env` carries a tunnel token. NEVER use in production. |
| `WEBHOOK_DEV_MODE` | `false` | Skip webhook signature checks on routes with no secret, and nothing else: API auth stays on and `API_KEY` is still required. Required for the smee.io relay. Startup refuses it when SSO is configured or the root `.env` carries a tunnel token. NEVER use in production. |
| `DATABASE_URL` | `postgresql://embry0:embry0@postgres:5432/embry0` | PostgreSQL connection |
| `MAX_BUDGET_USD` | `10.0` | Governed by the settings document (`budget.max_budget_per_job_usd`, the per-job ceiling). Read once, at the first start of the release that added the section, and only when no budget was ever saved with `PUT /config/budget` (that saved row won over it, and is imported instead); ignored after that. At or below `0`, or not finite, no ceiling. Keep it set while you may roll back: the release before reads it |
| `DAILY_BUDGET_CAP_USD` | `100.0` | Governed by the settings document (`budget.daily_cap_usd`). Read once, as `MAX_BUDGET_USD` is; at or below `0`, no daily cap |
| `MONTHLY_BUDGET_CAP_USD` | `500.0` | Governed by the settings document (`budget.monthly_cap_usd`). Read once, as `MAX_BUDGET_USD` is; at or below `0`, no monthly cap |
| `BUDGET_OVERRUN_MODE` | `soft` | Governed by the settings document (`budget.overrun_mode`). Read once, as `MAX_BUDGET_USD` is |
| `RATE_LIMIT_PER_AUTHOR_PER_HOUR` | `5` | Governed by the settings document (`budget.rate_limit_per_author_per_hour`). Read once, as `MAX_BUDGET_USD` is; at or below `0`, no limit |
| `API_RATE_LIMIT_PER_MINUTE` | `300` | API request rate limit |
| `MAX_WEBHOOK_BODY_BYTES` | `5242880` | Webhook request-body ceiling (bytes) |
| `MAX_RUNNING_JOBS` | `0` | Most jobs running at once across the deployment; `0` is no cap. A job past it waits in `pending` (the board's "queued" lane), its timeline says so, and it starts on its own when a running job ends — it is never failed for waiting. Every kind of job counts once: issue-to-PR, QA (whose own sub-tasks run up to the repo's `parallelism.max_concurrent_apps` sandboxes inside that one slot), onboard, pull request review, watcher and PR-comment jobs. A job paused for an answer (`awaiting_input`, `paused`) holds no slot, since its agent has stopped; its resume takes the next free slot ahead of jobs that have not started. Cancelling a queued job removes it before it runs. The queue lives in the orchestrator's memory, but each job records how to start it (`jobs.launch`), so after a restart the jobs still waiting are started again; only a waiting row written before that record existed (#307) is failed with `ERR_ORPHANED` and a message that it never started. Size it against DinD: [provisioning](ops/provisioning.md#sizing-dind-and-the-job-cap) |
| `SHUTDOWN_DRAIN_SECONDS` | `90` | On SIGTERM (a deploy, a restart) the orchestrator starts no more jobs and gives the running ones this long to reach their next node boundary, where LangGraph has saved them; a job still inside a node after it is stopped where it is. Every job stopped is resumed from its checkpoint when the orchestrator is back. Keep it under the orchestrator's `stop_grace_period` in `infra/docker-compose.yml` (180 s) minus uvicorn's 30 s and the rest of shutdown; see [deploy](ops/deploy.md#deploying-while-jobs-run) |
| `MAX_RESUME_ATTEMPTS` | `3` | How many times boot recovers one job after an unclean stop (a crash or kill, no drain) before failing it with `ERR_RESUME_LIMIT`, so a job that takes the orchestrator down cannot loop. Recoveries after a clean drain do not count. `0` turns recovery off: every in-flight job fails at boot, as before #307 |
| `ASK_USER_ROUNDS_CAP` | `10` | Agent ask-user rounds per job before `ERR_MAX_AGENT_QUESTIONS` |
| `USER_RETRY_ROUNDS_CAP` | `5` | User "continue retrying" rounds per job |
| `PROD_PORT` | `8200` | Frontend port (nginx) |
| `AGENT_RUNTIME` | `dind` | Which daemon runs sandboxes: `dind`, the privileged Docker-in-Docker service, or `rootless`, a dedicated rootless Docker daemon on the host. `rootless` needs `DOCKER_HOST=unix://…` and no `DOCKER_TLS_VERIFY`/`DOCKER_CERT_PATH`, refuses to start unless the daemon reports rootless with enforceable limits, and refuses `dind_enabled` profiles and QA `mode: dind`. Compose sets it through `infra/docker-compose.rootless.yml`; see [provisioning.md §10](ops/provisioning.md#10-a-rootless-sandbox-daemon) |
| `TELEGRAM_BOT_TOKEN` | — | Telegram bot token for notifications |
| `TELEGRAM_CHAT_ID` | — | Telegram chat ID for notifications. Also **the gate on inbound replies**: an update from any other chat is dropped with a silent `204`, and an empty value rejects every inbound update (the bot's secret token proves the update came from Telegram, not that it came from you). |
| `TELEGRAM_ALLOWED_SENDER_IDS` | — | Optional comma-separated Telegram user ids allowed to answer questions. Empty means anyone in `TELEGRAM_CHAT_ID`, which is already closed for a private chat; set it to narrow a shared group chat. Only numeric ids count: an entry such as a `@username` is not an id and never widens the gate, so a list with no numeric id admits nobody, and every answer then gets a silent `204` (the `telegram_update_rejected` warning lists such entries as `invalid_allowlist_entries`). |
| `TELEGRAM_WEBHOOK_URL` | — | Public URL for Telegram callback (e.g. Cloudflare tunnel) |
| `TRIGGER_LABELS` | `embry0` | Comma-separated labels that dispatch a job, on **every** trigger surface (GitHub, GitLab, and Linear alike). Matching is case-insensitive. Fires when an issue is opened carrying one, and when one is applied to an existing issue. An untracked issue is adopted on first trigger label. Only issues in `open` dispatch — a running or closed issue is synced but not re-dispatched. **Precedence:** this env var is the default; once Settings → Integrations has been saved, the `integration_config.trigger_labels` DB row wins. An empty DB value falls back here rather than disabling the trigger. Startup logs `trigger_labels_effective` with the effective label and its source (`db` / `env` / `default`), warns `trigger_labels_env_shadowed` when `.env` disagrees with the DB row, and warns `trigger_labels_env_empty` when the value holds no label (e.g. `,`) — such a value is ignored rather than disabling every trigger. |
| `LINEAR_API_KEY` | — | Linear personal API key. Drives the inbound label trigger and outbound write-back, not just the CLI helper. Also settable in Settings → Integrations, which wins when set. |
| `LINEAR_WEBHOOK_SECRET` | — | Signing secret for `POST /api/v1/webhook/linear`. Linear sends a **bare hex** HMAC-SHA256 in `Linear-Signature` — no `sha256=` prefix, unlike GitHub. Also settable in Settings → Integrations, which wins when set. |
| `LINEAR_REPO_MAP` | — | JSON object keyed by Linear project name **or** team key, mapping to `owner/repo`, e.g. `{"Acme Platform": "acme/backend"}`. An issue whose project is unmapped is ignored. Also settable in Settings → Integrations, which wins when set. |
| `LINEAR_RECONCILE_MODE` | `shadow` | Dispatch reconciler mode: `off` (never runs), `shadow` (takes every decision and changes nothing — no job, no ticket comment, no reopened issue; logs `linear_reconcile_would_dispatch` / `linear_reconcile_would_skip` / `linear_reconcile_would_reopen` once per ticket and again only when the decision changes), `on` (acts). Ships in `shadow`; a human promotes it to `on`. See `docs/webhooks.md`. |
| `VERIFICATION_MODE` | `shadow` | Deterministic verification after an approved review (`docs/verification.md`): `shadow` (decide and store; change no routing, write nothing to a forge), `on` (additionally fail a job on a NEW test failure, prune browser QA by tier, post the verdict and the `human-merge-only` label), `off` (skip the node). Ships in `shadow`; a human promotes it. An unrecognised value — and an absent config — are logged and read as `shadow`. The deployed-target QA fix is structural and applies in every mode. |
| `LINEAR_RECONCILE_INTERVAL_SECONDS` | `300` | Seconds between reconciler sweeps. `0` disables the loop; a sweep is a no-op while no Linear API key is configured. |
| `LINEAR_RECONCILE_STARTUP_DELAY_SECONDS` | `90` | The first sweep after a start waits this long (capped at the interval) instead of a whole interval. The last sweep is not persisted: a sweep is cheap and idempotent, and what it may start is bounded from the jobs table. |
| `LINEAR_RECONCILE_MAX_DISPATCHES` | `3` | Most jobs one sweep may start; the rest wait for the next sweep. |
| `LINEAR_RECONCILE_MAX_DISPATCHES_PER_DAY` | `5` | Most jobs the reconciler may start in a rolling 24 h, counted from `jobs.dispatched_by = 'linear-reconciler'` (survives restarts). Webhook dispatches do not count. |
| `LINEAR_RECONCILE_MAX_ATTEMPTS_PER_TICKET` | `2` | Most jobs the reconciler may ever start for one Linear ticket, counted the same way. Reaching it is commented on the ticket once; re-applying the label (the webhook path) is not bound by it. |
| `LINEAR_RECONCILE_FAILURE_MAX_ATTEMPTS` | `5` | A dispatch that raises before a job exists is retried by later sweeps with exponential backoff (one interval, doubling, capped at 6 h) and abandoned after this many consecutive failures (commented once). Counted in `tracker_dispatch_failures`; a successful dispatch resets it. |
| `MERGE_SYNC_MODE` | `shadow` | Merge sync sweep (#279): `shadow` (the default) logs `merge_sync_would_record` and writes nothing, `on` records, `off` never starts the loop. Its GitHub calls are read-only and it never dispatches, comments or pushes — but it does WRITE here (`jobs.delivery_state`, `jobs.status` `completed → pr_merged`/`pr_closed`, `jobs.pr_url`, the embry0 issue closed on merge, healing-case rows), unattended, so it ships in shadow like every other unattended writer. Promote it to `on` after reading one sweep's `merge_sync_would_record` lines. **The mode gates only the sweep:** the `pull_request` webhook records through the same code in every mode, `off` included — a delivery is a fact that arrived, not an action embry0 chose to take. A value outside the three is logged `CRITICAL` (`merge_sync_mode_invalid`) and treated as `off`; it cannot stop startup. See `docs/webhooks.md`. |
| `REPO_RENAMES` | — | GitHub repos this deployment renamed, as a JSON object of old `owner/repo` to current `owner/repo`, e.g. `{"acme/old-name": "acme/new-name"}`. GitHub redirects an old URL, so it still opens, but it no longer equals the URL GitHub reports for the same PR, and merge sync matches on equality. With a rename configured, merge sync, the `pull_request` webhook and the healing ledger match a stored PR or issue URL under either slug, and an API key's [repository allowlist](api.md#repository-allowlist) matches either slug too; nothing rewrites stored rows. Renames are single-hop: map every old name straight to the current one (an entry pointing at a slug that is itself renamed is refused). Read at startup, by the orchestrator and by `embry0 merge-sync`; a value or entry that does not parse is logged as `repo_renames_invalid` and skipped, it cannot stop startup. Empty renames nothing. |
| `MERGE_SYNC_INTERVAL_SECONDS` | `900` | Seconds between sweeps (the first runs one minute after startup). `0` disables the loop. |
| `MERGE_SYNC_MAX_REQUESTS` | `60` | Most GitHub API requests one sweep may make. A sweep that runs out resumes from its keyset cursor on the next interval (in memory: a restart starts the pass from the oldest unsettled PR again). |
| `MERGE_SYNC_MAX_WRITES` | `200` | Most job rows one sweep may change before it stops and leaves the rest to the next one — the bound a request budget cannot give, since one listing request can yield many facts. An operator's `merge-sync backfill` is deliberate and is not write-budgeted. |
| `MERGE_SYNC_RATE_LIMIT_FLOOR` | `500` | The sweep stops as soon as GitHub reports fewer than this many requests left on the token (`X-RateLimit-Remaining`), or answers 403 / 429, leaving the quota to the pipeline. |
| `MERGE_SYNC_LIST_PAGES` | `1` | Pages (100 PRs, most recently updated first) listed per repo when looking for a PR that someone else opened from a job's branch. |
| `MERGE_SYNC_UNLINKED_LOOKBACK_DAYS` | `30` | Only repos with a code job younger than this and no PR URL are listed. Older history is the backfill's job (`python -m embry0.cli merge-sync backfill`). |
| `LINEAR_RECONCILE_STALE_TRIAGING_MINUTES` | `15` | The reconciler reopens Linear-tracked issues that have sat in `triaging` this long with no live job (the orchestrator died between claiming the issue and inserting the job). `0` disables. |
| `GITLAB_URL` | `https://gitlab.com` | GitLab origin. Set to your host for self-managed; `/api/v4` is appended automatically. Must be an `https://` URL with a hostname — the orchestrator refuses to start otherwise, because plaintext would send the `PRIVATE-TOKEN` in the clear and a scheme-less value builds a nonsense API base that silently falls back to github.com. A trailing slash is stripped; empty means the default. |
| `GITLAB_TOKEN` | — | GitLab access token. A `glpat-` PAT is sent as `PRIVATE-TOKEN`; an OAuth2 token (`gloas-`) as `Authorization: Bearer`. Empty disables the integration. |
| `GITLAB_TOKEN__<NAMESPACE>` | — | Per-namespace override, keyed on the **top-level group** (`acme/products/widgets` → `GITLAB_TOKEN__ACME`). Punctuation becomes `_`. |
| `GITLAB_WEBHOOK_SECRET` | — | Value GitLab sends in `X-Gitlab-Token`. Compared **verbatim** — it is a shared secret, not an HMAC like GitHub's or Linear's. |
| `GITLAB_REPO_MAP` | — | Optional JSON map of GitLab project path → target repo. Usually unnecessary: a GitLab project *is* the repo, so resolution defaults to identity. |
| `GITLAB_CA_BUNDLE` | — | Path **inside the orchestrator container** to a PEM bundle for a self-managed instance behind a private CA. Read once at startup and fanned out to all three clients that break without it — orchestrator `httpx`, the gitlab-proxy, and git inside every sandbox (which gets the system store *plus* this CA written to `/home/agent/.embry0/ca-bundle.pem`, so public hosts keep working). An unreadable path, or one whose contents are not a certificate, **refuses the boot** and names the path. Empty is correct for gitlab.com. |
| `GITLAB_CA_BUNDLE_HOST` | `/dev/null` | Compose-only companion: the PEM's path **on the host**, bind-mounted read-only at `/etc/embry0/gitlab-ca.pem`. Set both this and `GITLAB_CA_BUNDLE` (to that in-container path), or neither — this one in `infra/.env` (compose interpolation), `GITLAB_CA_BUNDLE` in the repo-root `.env` (the container's env, ADR 0005). The two failure modes differ: `GITLAB_CA_BUNDLE` alone refuses the boot (it reads the inert `/dev/null` mount), while this one alone is a silent no-op — the PEM is mounted, never read, and clones fail their handshake later. |
| `DEFAULT_FORGE` | `github` | Forge assumed for repos that were never registered in the repo registry. Empty (`DEFAULT_FORGE=`) refuses them: the job fails with `ERR_REPO_UNREGISTERED` before any sandbox is created, naming the repo and telling the operator to register it. Whatever its value, a **dispatch** to an unregistered repo is refused (#360): a tracker trigger (Linear, GitHub, GitLab), an issue dispatch through the API, an accepted watcher finding and a watcher tick all check the registry first — under every spelling `REPO_RENAMES` gives the repo, case-insensitively — and Linear says so on the ticket once. So the default forge only matters for a job submitted straight to `POST /jobs`. **Registration is manual, with two exceptions:** a GitHub delivery for an unregistered repo under an active organization whose `settings.auto_register` is true registers it under the organization's forge ([webhooks.md](webhooks.md#organization-webhooks-github)), and storing a QA config (`PUT /api/v1/repos/{repo}/-/qa-config`) registers its repo under `DEFAULT_FORGE`. Any other repo must be registered before its first job, via `POST /api/v1/repos` (`{"repo": "<path>", "forge": "gitlab"}`) or the MCP `repo_register` tool. With `DEFAULT_FORGE` empty, a registration that omits `forge` is refused with 422 rather than guessed, and storing a QA config no longer auto-registers (it would have to invent a forge) — register the repo first. |
| `ENVIRONMENT_SECRET_KEY` | — | Fernet key for encrypting env var secrets at rest |
| `API_KEY` | — | **Required** unless `AUTH_DEV_MODE=true` — bearer key for the orchestrator API. Startup refuses an empty value otherwise, `WEBHOOK_DEV_MODE` included. Generate with `python -c 'import secrets; print(secrets.token_hex(32))'`. |
| `PROXY_ADMIN_TOKEN` | — | Required, gates the credential proxies' admin endpoints. Generate with `python -c 'import secrets; print(secrets.token_urlsafe(32))'`. |

DinD needs no credential: the CLI sends it with each pull and push. Set but unreadable, or set with `IMAGE_REGISTRY` empty, **refuses the boot**. Empty: no login is written. |
| `IMAGE_PINS_FILE` | — | **Set by compose, not `.env`.** The digests `init-push-images` recorded as it pushed the embry0 images, one `<name>:<tag> <digest>` per line (#523). A missing or malformed file, or one without a pin for `embry0-proxy:latest` and every builtin sandbox image, **refuses the boot**. Empty: images run by tag, and startup warns `image_pins_not_configured` when `IMAGE_REGISTRY` is set. |
| `SKILLS_STORE_PATH` | `/skills` | Where the orchestrator syncs [skill sources](api.md#skills) to: `/skills/<source_id>/<resolved_sha>/` plus a `/skills/<source_id>/current` pointer. Under `AGENT_RUNTIME=rootless` set it to the host directory the rootless daemon sees ([provisioning.md](ops/provisioning.md#10-a-rootless-sandbox-daemon)) |
| `SKILLS_PATH_ROOT` | — | The directory, inside the orchestrator container, that a `path` [skill source](api.md#skills) must resolve under (symlinks resolved first); a source outside it fails its sync. | `OFFHOST_BACKUP_S3_PATH` | — | `<bucket>/<prefix>` the `offhost-backup` compose service (profile `offhost-backup`) copies the Postgres dumps and every MinIO bucket to, off the host. Set it together with the profile. See [backup-restore.md](ops/backup-restore.md#off-host-copy) |

| `PAUSED_JOB_TTL_HOURS` | `48` | Hours before a paused job's sandbox is expired |
| `VOLUME_REAPER_ENABLED` | `true` | DinD volume reaper (#274): a sweep at startup and every `VOLUME_REAPER_INTERVAL_SECONDS` that removes per-job QA volumes whose owning job is terminal or has no `jobs` row. Ownership is read from the `embry0.managed` / `embry0.volume_scope` / `embry0.job_id` labels stamped at volume creation; volumes of live jobs, per-repo volumes and anything embry0 did not create are never touched, and removal never uses `--force`. **Instance scoping (not a setting):** every volume is also stamped `embry0.instance=<id>`, where the id is derived at startup from PostgreSQL's cluster `system_identifier` plus the database name (`embry0/storage/instance_id.py`; logged as `volume_instance_id_resolved`). ### Proposal and job briefs

Both loops are one brief writer (`embry0/services/brief_writer.py`), each on its own interval and per-tick count below. Each tick reads its model from one snapshot of the settings document ([background models](providers.md#background-models)) and its voice from an agent definition, so a change to either needs no restart.

**A brief's voice is an agent definition; its format is embry0's.** A brief's request is a voice, then a format. The voice says who the brief speaks to and how: its language, tone and style. It is the system prompt of the built-in agent `proposal-brief` or `job-brief`. Change it like any agent's: on the Agents page (under *Background writers*), with `PUT /api/v1/agents/{type}` (`{"system_prompt": "..."}`), or with the MCP tools `agent_get`, `agent_update` and `agent_reset`.

- **The format stays embry0's.** The answer's JSON keys, their lengths and the rules the parser holds it to are added after every voice, so a voice in German still gets answers embry0 reads. A voice that defines one of those keys, a quoted key and a colon such as `"title": ...`, is refused with 422. Anything else is accepted: a voice may name JSON, quote a word or carry a glossary, and the format that follows it overrides whatever else it says about the answer.
- **An edit rewrites the briefs already written**, a few a tick after any missing or stale one, within the per-tick count and the budget caps. Each brief records the prompt it was written with. A brief written before the voices records none, which stands for the prompt sent then, so a release that rewords the shipped voice rewrites none of them while the row still holds the voice. Every brief stays shown until its rewrite replaces it.
- **No voice falls back to the shipped one.** A definition with an empty voice, or none, writes with the voice the release ships, and `agent_reset` puts that voice back.
- **A name the deployment already used stays its own.** An agent the deployment made itself as `proposal-brief` or `job-brief` before this release keeps its prompt and still runs in jobs. The seeder leaves it, `agent_reset` refuses it, and the brief writer writes with the shipped voice and logs `brief_voice_name_taken` once. To edit the voice, make that agent again under another name and delete it: the next start seeds the voice.
- **The voices are the deployment's.** An organization cannot have its own.
- **They run in no job** (`runs_in_jobs` false on their rows). They are not pipeline steps, not per-agent models on the job form, and not guild characters, and their own model is not read: a brief runs on `background_models.proposal_brief` or `job_brief`.

### Watched stacks (#378)

What embry0 watches is a **row per stack** in `watcher_stacks`, not a set of
env vars: `repo` (the scope key every watcher table already uses), its LogQL,
which tracker its findings are filed into, and `settings` — **overrides
only**, so an absent key inherits the `WATCHER_*` default below.

```
GET    /api/v1/watcher/stacks                 # every stack + the overridable keys
PUT    /api/v1/watcher/stacks/{owner}/{name}  # create or replace (admin)
DELETE /api/v1/watcher/stacks/{owner}/{name}  # stop watching (admin); its runs, signatures and cases stay
```

A deployment upgrading from the env-var watcher seeds its stack from
`WATCHER_REPO` / `WATCHER_LOGQL` / `WATCHER_LINEAR_*` at startup, **once, and
only while the table is empty** — after that the table is the source of truth
and re-seeding would resurrect a stack someone deleted. The `WATCHER_*`
settings below remain the defaults every stack inherits.

An unknown key in `settings` is dropped on write and echoed back as
`ignored_settings`, so a typo cannot become configuration nothing reads.

One key has no `WATCHER_*` default: `signature_masks`, a list of
`{"pattern", "replacement"}` that masks a record-id format only that
stack's logs carry, so its lines stop becoming one log signature per id.
The built-in masks it adds to live in code
(`embry0/services/log_signatures.py`). A stack's masks apply first, at most
50 of them, each pattern a Python regular expression of at most 500
characters; every tick reads them, so a change needs no restart. See
[self-watching.md](self-watching.md#signature-masks).

| Variable | Default | Description |
|----------|---------|-------------|
| `WATCHER_ENABLED` | `false` | Start the scheduled log-watcher/proposer loop (Loki scan → analysis job → draft ticket). The ticket is filed through the stack's **draft filer** (`embry0/services/draft_filers.py`): a Linear team today, or a GitHub repo for a stack whose tracker is GitHub Issues. Filing never applies the trigger label — that is the human's acceptance step. |

The `\|~` match is on the message **body**, so without the trailing stage expression it also selects DEBUG/INFO lines that merely contain the word "error" — 17.6% of the stream as measured on a production stack (#368). | `CONFIRM_HEALED_ENABLED` | `true` | After a case's deploy marker, count its signature and record a `healed` / `not_healed` / `inconclusive` verdict with the counts behind it (#312). **On** rather than shadow, unlike every other autonomy stage, because it only reads the ledger and comments on the ticket — its one ledger write besides the verdict is sending a `not_healed` case back to `tracked`, at most once per case (#451), where a person accepts the retry or closes the case (#658); it dispatches nothing. Refusals for CI, the gate or mergeability leave the ask `pending`, answerable again; a moved head makes it `stale` and posts a fresh ask. Denylisted paths (migrations, auth, infra, CI, dependencies, secrets) are flagged in the ask but do not block — the denylist stops machine merges, and this is a human's. | `WATCHER_DEPLOY_LOGQL` | — | LogQL whose every matching line is one deploy marker in the analysis briefing, e.g. `{job="my-stack-deploy"}`; a `deployed <sha>: <services>` line also anchors healing cases to the deploy that shipped their fix. A watched stack can override it with its `deploy_logql` setting. |

| `AUTH0_CLIENT_ID` / `AUTH0_CLIENT_SECRET` | — | Confidential-client credentials on your Auth0 tenant |
| `SESSION_SECRET` | — | Signs the SSO session cookie (>=32 chars); rotation logs everyone out |

See `.env.example` for the complete list.

Unknown variables are ignored rather than rejected (the env is shared with Docker and the shell), so at startup — and in `embry0 config` — a variable that near-misses a setting is flagged as `unknown_env_var name=AUTH_DEV_MOD did_you_mean=AUTH_DEV_MODE`; it is a warning only and never blocks boot.

`embry0 config` masks every credential setting, and so does a config object written to a log. A secret shorter than 24 characters is shown as `****`; a longer one keeps its first and last four characters, enough to tell two tokens apart. An unset secret is shown empty. Any URL keeps its scheme, host, port and path but not its user or password, since a token is often written as the bare user (`DATABASE_URL=postgresql://****@postgres:5432/embry0`), and query parameters such as `password=`, `token=` or `sig=` are masked too. A configuration that does not load names each variable and why, never its value.

## Secrets at rest

embry0 encrypts per-repo secret environment variables at rest using Fernet, keyed by `ENVIRONMENT_SECRET_KEY`:

```bash
# Generate a strong key (or use your favorite secret manager)
openssl rand -hex 32
```

The same key also protects the [credential registry](credentials.md) (`credentials`): forge tokens, and LLM and SSH credentials in later releases. Tailnet API keys, which a [hosts](hosts.md) import and probe read devices with, are registry credentials too.

In production the orchestrator refuses to start without a real key; in dev mode a default is tolerated with a loud warning. The key is rotatable without orphaning anything: move the current key into `ENVIRONMENT_SECRET_KEYS_OLD` (comma-separated, newest first), set a fresh `ENVIRONMENT_SECRET_KEY`, and restart — decryption tries every listed key while encryption always uses the current one. Replacing the key *without* carrying the old one in `ENVIRONMENT_SECRET_KEYS_OLD` makes previously encrypted values undecryptable: an env-var secret logs `secret_decryption_failed` on the next job that needs it, and a registry credential is marked `disabled` with `status_reason=decryption_failed` on its next resolution and skipped until `POST /api/v1/credentials/{id}/rotate` re-enters its secret.

Per-repo and global env vars are managed through the `/environments` page in the dashboard.

## Runtime configuration (API)

Budget controls, context injection, and sandbox profiles are configurable via the API without restarting:

- **Budget** — the settings document's `budget` section (below), on the General tab, the Policy tab, `PATCH /api/v1/config/settings/budget`, `embry0 settings set budget ...` and the MCP tool `settings_set_keys`. Admin only. `GET/PUT /api/v1/config/budget` is deprecated and removed in 0.2.0 ([api.md](api.md#runtime-configuration)). See [architecture.md](architecture.md#budget-controls) for where each limit is enforced.
- **Context** — `GET/PUT /api/v1/config/context` (global), `/config/context/repos/{repo}` (per-repo)
- **Providers** — `GET/PUT /api/v1/config/provider`: the tier models, the default model, disabled models, the fallback order and `local_max_runs`. A saved row wins over `MODEL_*` and `DEFAULT_MODEL`. The model background features run on is the settings document's `background_models` section (below); `PUT` refuses the old `watcher_local_model` with a 422 naming it. See [providers.md](providers.md)
- **Sandbox Profiles** — `CRUD /api/v1/sandbox-profiles`. A profile's `dind_enabled` only asks for the shared Docker daemon; a sandbox gets it when an admin has also granted its repo Docker access (`PUT /api/v1/repos/{repo}/-/docker-access`, or the repo page). Code from a granted repo can control the shared Docker daemon, including the proxies holding your tokens. Without the grant, a sandbox on such a profile (the builtin `qa-jvm` included) is refused at creation. A profile cannot weaken a sandbox's isolation: `cap_drop` must include `ALL`, `cap_add` must be empty, `security_opt` may hold only `no-new-privileges`, `base_image` must name an image in embry0's own registry without a registry host, and `extra_networks` may hold only `sandbox-internet`. The API refuses other values with a 422, and a sandbox on a stored profile that holds one is refused at creation. A sandbox's memory and CPU limits are its profile's `memory` and `cpus`; there is no global setting. The builtin profiles are re-seeded at every startup, overwriting edits, so set different limits on a profile of your own.

- **Hosts**: `GET/POST /api/v1/hosts`, `GET/PATCH/DELETE /api/v1/hosts/{id}`, `POST /api/v1/hosts/{id}/probe` and `POST /api/v1/hosts/import/tailnet`. The machines that run the code, how embry0 reaches each one, where its logs come from, and which repositories it serves. A tailnet import and a tailnet probe read devices with a `tailnet_api_key` credential bound at global scope with role `tailnet`; no environment variable configures it. See [hosts.md](hosts.md).

- **Progression content pack**: `GET/PUT /api/v1/progression/pack`, the draft (`GET/PUT/DELETE /api/v1/progression/pack/draft`, `GET /api/v1/progression/preview`, `POST /api/v1/progression/pack/draft/activate`), the versions with restore, and `POST /api/v1/progression/pack/reset`. The skills, rates, tiers, rares, achievements, quests, diaries, words and timezone of the progression layer; one pack per deployment, the shipped default until an admin activates another. No environment variable configures it. See [progression.md](progression.md#changing-the-content).

- **Standards**: `GET /api/v1/standards/{owner}`, `GET/PUT /api/v1/standards/{owner}/{kind}`, `GET /api/v1/standards/{owner}/{kind}/versions`, `GET/PUT /api/v1/standards/{owner}/{kind}/repos/{repo}` and `POST /api/v1/standards/{owner}/{kind}/audit/{repo}`. An owner's versioned standards (schema and values), each repository's mode under them, and audits against them. An organization's values are configuration stored here; no environment variable configures them. See [standards.md](standards.md).

- **Context audit**: `PATCH /api/v1/orgs/{owner}` with `{"settings": {"context_audit_days": N}}` (1 to 365, `null` for off, the default) audits the files that steer a coding agent in each of the owner's registered repositories on a schedule, and `GET /api/v1/orgs/{owner}/context-audit` reads what it sees. The interval lives on the organization row; its two caps are the `budget` section's `context_audit_job_usd` and `context_audit_max_jobs_per_tick`, in the organization's layer for its own. See [context-audit.md](context-audit.md).

See [api.md](api.md) for request examples.

## Settings document

Operator policy moves out of environment variables into one settings document per deployment, stored in the database ([ADR 0026](adr/0026-settings-document.md), [spec](superpowers/specs/2026-10-28-settings-documents-design.md)). Each feature owns one section of it. A change applies on the next tick of the loop that reads it, or to the next job that starts for a section a job reads, with no restart.

```yaml
# Every key is optional; an absent key takes its default (the reference below).
version: 1
asks:
  enabled: true
  hours: "08-17"
  weekdays: mon-fri
  timezone: Europe/Berlin
```

- **Read** it with `GET /api/v1/config/settings` (`?format=yaml` for the text alone), every setting's effective value and where it came from with `GET /api/v1/config/settings/effective`, and the JSON Schema with `GET /api/v1/config/settings/schema`. Any key can read: the document holds no secrets.
- **Write** it with `PUT /api/v1/config/settings`, the whole document as YAML (comments are kept) or as a JSON object. Admin only, with a key that has no repository allowlist. A 422 lists every bad key at once, a key written twice included; `?dry_run=1` answers what would change and stores nothing; `If-Match: "<generation>"` (the `ETag` of a GET) refuses a write over a newer one with 409, on a dry run too.
- **Change a key or two** with `PATCH /api/v1/config/settings/{section}` and a JSON object of that section's keys, `{"remind_hours": 12}`; `null` takes a key out, back to its default. The keys go into the stored text where they stand, so its comments and layout stay, and the rest of the document is left as it is: for a page that edits one setting as a form field, outside the Policy tab, and for `embry0 settings set` and the MCP tool `settings_set_keys` below. It follows every rule of a `PUT`, the whole document it makes checked, `If-Match`, `?dry_run=1`, the revision (source `person`, with `?reason=`) and the audit row included ([api.md](api.md#settings-document)).
- **History.** Every write that changes the text is a revision with its actor and source: `GET /api/v1/config/settings/revisions`, and `POST /api/v1/config/settings/revisions/{id}/undo` for the newest one. The newest 100 are kept.
- **In the dashboard**, Settings → Policy holds the same three things, for one document at a time. The **Layer** picker above them chooses the deployment's document, an organization's layer or a repository's: it offers every organization and repository the lists show and every stored layer, each marked with how many keys its layer sets, and keeps the choice in the URL (`/settings?tab=policy&owner=acme`, `&repo=acme/widgets`), so a layer can be linked to; an organization's Settings tab and a repository's page link to their own. Picking one with no layer opens an empty one that its first save creates, and picking another while an edit is unsaved asks first. The document is a YAML text box: **Preview** runs the dry run and lists each key the text would change, before and after, with the text diff; **Save** then stores exactly the previewed text, with an optional reason. Both name the generation the edit started from (0 for a layer nobody wrote), so if someone else saved in between they are refused, the new version is read in and your text stays in the box to preview again. A layer lists above its text the keys it may set, per section. A refused document lists every problem next to the text, each with its key, and marks a key the layer may not set. When a save, its preview or an undo makes values of the layers under the document read as inherited (`layers_refused`), the tab lists them, each linked to its layer. Below it, **Values in effect** shows every key of every section with its value, its default and where it came from, and warns when a stored value is refused, an imported variable is still set, or the document holds a section or key this release does not know; for a layer, as that organization or repository reads it: the layer each value comes from, what the layer's own value overrides ("Overrides "09-18" from the deployment"), what it inherits and from whom, and, dimmed, the keys it may not set. **History** lists the document's revisions, opens each one to show what it changed, and offers Undo on the newest. Anyone signed in can read the tab, with the people behind changes shown as the audit log shows them (someone else's name only to an admin); only an admin can preview, save or undo, and an API key with a repository allowlist only on a repository's layer the list covers. A document [kept in a file](#from-a-file-the-command-line-and-mcp) is shown read-only, to an admin too.
- **From the environment.** When a release moves a feature's policy into a section, the first start of that release imports each of its variables you set, when the value differs from the default, once per key (source `bootstrap`); a key a later release adds to the section is imported at that release's first start. A variable left at its default is not imported, so a default the section changes reaches every deployment that never set it; where a section turns a default the other way on purpose, it declares the value a deployment that relied on the old meaning keeps, and how to tell one from its records (for `leads.enabled`: a registered repository, a job or a lead a finder stored). Only records older than the moment the release first asked about the key count: the import records that moment once in the document's ledger (`leads.enabled@<time>`, the database's clock when the process began, before the migrations), so a repository a new deployment registers while it waits, or between two starts, is never taken for its past. While the variable is not set, such a deployment gets that value written into the document under a comment saying why (`settings_default_kept`, once); a new one does not, and a value an operator has written stands. If that check fails (the database busy at the start), its key reads its default, `settings_bootstrap_check_failed` is logged at error level, and the check is asked again in the same run, after a minute and then at doubling intervals up to fifteen minutes, until it answers (`settings_bootstrap_check_settled`); a restart in between asks at its start, about the same moment. An import that fails outright is tried again in the same run the same way. A part of a variable the section drops, such as an unknown finder name in `LEADS_FINDERS`, is named in a `settings_env_value_dropped` warning. A value the section refuses is skipped with a `settings_bootstrap_value_refused` warning: set it in the document instead. A value refused only together with the section's other stored values is held (`settings_bootstrap_value_held`) and tried again at the next start. After that the variable is ignored: startup logs `settings_env_ignored` and `embry0 config` says the document governs it. The variable is removed one release later. The reference below names the variable each key was imported from.
- **After a rollback.** A section or a key that a newer release wrote and this one does not know is kept as long as it is sent back exactly as stored (as the stored text has it, or as GET's `data` does), and is listed in `unknown_sections` or `unknown_keys`.
- **Layers by organization and repository** ([ADR 0028](adr/0028-settings-layers.md)). An organization and a repository can each have a layer: a document of the same shape that holds only what it sets, read and written with `?owner=acme` or `?repo=acme/widgets` on the same routes, recorded and undone the same way. A key takes the value of the most specific layer that sets it (the deployment's document, then the organization's layer, then the repository's), and a layer replaces an inherited value whole. The one exception is `leads.ask_severities`, merged kind by kind: the deployment's document over the default, and an organization's layer over the deployment's. The kinds a document names replace the entries below it; every other kind keeps them (the reference marks it *entry by entry*, and the effective view gives each kind's source in `entries`). A repository belongs to the organization named by the first segment of its slug, so a GitLab project in a subgroup belongs to its top group; work with no repository reads the deployment's values. Each section says which of its keys an organization or a repository may set (the "Overridable by" column below); setting any other is a 422 naming the key. A value refused together with what it inherits is a 422 when written; if a later change below it makes it so, it is read as the inherited value, a `settings_layer_value_refused` warning is logged once per snapshot that reads it, and the write that caused it lists it in `layers_refused`. A repository renamed with `REPO_RENAMES` still reads the layer written under its old slug, and the first change made through `?repo=` with the new slug moves the layer to it, with its history, so the rename entry can later be removed. `GET /api/v1/config/settings/effective?repo=acme/widgets` shows what that repository reads, each key with the layer it came from and the value it overrides. Writing a layer takes an admin, with a key without a repository allowlist for an organization's layer, or one whose allowlist covers the repository for a repository's. The organization or repository must be registered.
- **Moved so far**, one section per bullet, in name order:
  - The asks policy (`asks`, from `ASKS_ENABLED` and the `ASK_*` variables): the ask loop reads it every tick and `GET /api/v1/asks/due` on every request, so turning asks on or changing their hours needs no restart. It is read per organization: an ask follows the layer of the organization its decision's repository belongs to for `hours`, `weekdays`, `timezone`, `remind_hours`, `expire_days` and `max_open_per_person`, and the deployment's document for the rest, so a change to an organization's layer applies to its asks on the next tick. An ask about a decision with no repository follows the deployment's document. `max_open_per_person` counts per person within an organization: someone asked about two organizations' decisions may hold each one's number, and the asks about decisions with no repository count apart. `enabled` and `tick_seconds` are the deployment's alone.
  - Which repositories the background features read (`background`, from `SCOUT_REPOS`, `SCOUT_EXCLUDE`, `SLOP_METER_REPOS` and `SLOP_METER_EXCLUDE`, and what the scout and the Slop-O-Meter read before, into the repositories' layers): one switch per feature, `leads`, `scout` and `slop_meter`, which an organization's layer and a repository's layer may each set. A repository is read when it is registered, active and its switch resolves to true; nothing else enrolls it, not a job run on it. The scout and the meter are off until enrolled, and leads read every repository someone answers for unless a layer takes it out. Each loop reads it every tick, so opting a repository out stops it on the next one, and the meter removes what it kept of it `background.prune_after_days` (a week) later unless it comes back first ([which repositories](#which-repositories-background-features-read)).
  - The models background features run on (`background_models`, from `CONTEXT_AUDIT_LOCAL_MODEL`, `SCOUT_MODEL`, `PROPOSAL_BRIEF_MODEL` and `JOB_BRIEF_MODEL`, and the provider settings' `watcher_local_model` as its `default`): one key per feature and a default, and no feature falls back on another's model any more. Every feature reads it every tick. The default, the watcher and the context audit take only a model of your own server, and the scout runs only on a model named for it; a hosted model may be named for the briefs, the judge and the scout, and its calls outside a job are counted against the budget caps. A model is checked against the provider catalogue when it is written ([background models](providers.md#background-models)).
  - The budget (`budget`): every spending cap in one place. The fleet limits the `budget_config` row held (the per-job ceiling, the daily and monthly caps, the per-person rate limit, the overrun mode; edited on the General tab), the unattended jobs' caps (`CONTEXT_AUDIT_JOB_BUDGET_USD`, which capped the context audit, the area mapper and a finding's fix alike, now one key each, and `CONTEXT_AUDIT_MAX_JOBS_PER_TICK`), and how far a person may continue a job past its cap (the literal 1,000 a continue could name, whether a continue may pass the ceiling, and what one adds by default). The dispatch gate reads it at every dispatch and a job at every check of its cap, so a change holds from the next one with no restart. The first start of the release imports the saved `budget_config` row once, when one was ever saved, since it won over the variables; otherwise the variables. Each organization's `context_audit_budget_usd` and `context_audit_max_jobs_per_tick` were copied into its layer once ([api.md](api.md#organizations)). **No cap:** for the four fleet limits `0` is no limit, as their variables always read it, and a key left out reads its default; `null` is refused, so an empty value never lifts a cap. ### Which repositories background features read

The leads finders, the scout and the Slop-O-Meter each read a repository when it is registered, active and enrolled in that feature: its key of the `background` section resolves to true, through its organization's layer and its own (*Layers by organization and repository* above). Each loop reads the section from the snapshot it takes at the top of a tick, so a change applies on the next tick, with no restart. Making a repository inactive stops every feature reading it and removes nothing.

An organization's layer enrolls every repository of it (`PUT /api/v1/config/settings?owner=acme`):

```yaml
background:
  slop_meter: true
  scout: true
```

and a repository's layer takes one of them out again (`PUT /api/v1/config/settings?repo=acme/vendored`, or `embry0 settings set background slop_meter=false --repo acme/vendored`):

```yaml
background:
  slop_meter: false
```

The deployment's document sets the default of every repository no layer decides for.

**Which layer wins.** A repository's own layer outranks its organization's, which outranks the deployment's. The upgrade (below) writes `true` into the layer of each repository the scout or the meter read before, so `slop_meter: false` in an organization's layer or the deployment's document does not reach those: their own `true` wins. To take such repositories out, take the key out of each one's layer, or set it to false there: `embry0 settings set background slop_meter=null --repo acme/widgets` (`null` takes the key out, so the repository inherits its organization's value again), or `PATCH /api/v1/config/settings/background?repo=acme/widgets` with `{"slop_meter": null}`. Each is one revision of that repository's layer, undoable. There is no one call for many repositories; `GET /api/v1/config/settings/layers` lists every layer with the keys it sets, so for every repository of `acme`:

```sh
curl -s -H "Authorization: Bearer $EMBRY0_API_KEY" "$EMBRY0_API_URL/api/v1/config/settings/layers" \
  | jq -r '.layers[] | select(.layer == "repository" and .owner == "acme" and (.keys | index("background.slop_meter"))) | .repo' \
  | while read -r repo; do embry0 settings set background slop_meter=null --repo "$repo" --yes; done
```

then set `slop_meter: false` in `acme`'s layer.

| Key | Default | What a repository enrolled in it gets |
|---|---|---|
| `leads` | `true` | The leads finders read it when the leads loop runs and someone answers for it (owners set, or a watched stack): enrollment narrows that rule, it never widens it. `false` takes a repository, or an organization, out; the leads already stored stay until answered. `POST /api/v1/leads/run` with a `repo` runs a pass on that repository whatever its switch says |
| `scout` | `false` | The scout starts read-only scouting jobs on it and its areas, on `background_models.scout`. A scouting job of a repository taken out adds no leads when it finishes |
| `slop_meter` | `false` | The meter keeps a bare mirror of it and reads its history and forge events. An inactive one is not read and keeps what was read. One that leaves, by `false` or by being unregistered, loses its mirror and every row the meter kept of it, its contributors' names, emails and logins included, `prune_after_days` later, unless it comes back first; no tick removes anything while the registry read lists no repository at all ([what each feature keeps](ops/background-data.md)) |
| `prune_after_days` | `7` | The deployment's alone, 1 to 365: how long the meter waits after a repository leaves its scope before it removes what it kept of it. The wait starts at the first tick that finds it out of scope, and nothing shortens it |

**Upgrading.** Before this section, the scout and the meter read every registered, active repository the world map showed (a job in the last 90 days, owners, or an enabled watched stack), plus `SCOUT_REPOS` or `SLOP_METER_REPOS` and minus `SCOUT_EXCLUDE` or `SLOP_METER_EXCLUDE`. The first start of this release keeps exactly that set and nothing more:

- it records, once, the moment the process that first runs it began, read before the migrations, as the environment import does for `leads.enabled` (`background.<feature>@<time>` in the deployment's import ledger). Once recorded, every later try counts against it. A first start that fails before it records it tries again in the same run, with that same process start; only a restart before any try has succeeded records the new process's start instead;
- each repository that was registered and active then, with a job created in the 90 days before that moment, owners, or an enabled watched stack, gets `<feature>: true` in its own layer, under a comment saying why (revision source `upgrade`, actor `embry0:bootstrap`). Each inactive registered repository the meter keeps rows for gets `slop_meter: true` too: it is not read while inactive, and keeps what was read;
- each registered, active repository the include variable names gets `true`, and each registered one the exclude variable names gets `false`, which wins as it did and keeps the repository out if its organization is enrolled later (revision source `bootstrap`). An include name that is not registered, or names an inactive repository, is logged at error level (`background_enrollment_name_skipped`, with the variable): the feature read it before, whatever the registry said, and no longer does. The meter removes what it kept of one not registered `prune_after_days` after its first tick unless it is registered and enrolled first; an inactive one keeps its rows (above). An exclude name that is not registered excludes nothing;
- a registered name no settings layer can be stored under (an owner starting with a dot) is a failed write, logged at error level (`background_enrollment_name_unaddressable`): until it is renamed or unregistered the features stay unmarked, and the meter removes nothing;
- the feature is marked imported (`background.<feature>`), and the variables are ignored from then on: every start logs `settings_env_ignored` while one is set, and `embry0 config` says so.

From then on a job enrolls nothing: a repository that would have entered the old set later, or aged out of its 90 days, stays as its layer says until an operator changes it. A new deployment registered nothing before its first start, so it enrolls nothing and both features start off. Until a feature's import has run (one that failed is tried again in the same run, and at the next start), it reads its defaults and the meter removes nothing. After it has run, everything the meter keeps of a repository the import did not enroll is pending removal, a week after the meter's first tick: [what the background features keep](ops/background-data.md) gives the query that lists it before the upgrade. Leads import nothing: their default keeps every deployment reading what it read. The context audit (an organization's `context_audit_days`) and the log watcher (its stacks) keep their own opt-ins.

### From a file, the command line and MCP

You can keep the deployment's settings in a file in your own repository, review a change to it like any other, and store it with `embry0 settings apply`. [`docs/examples/settings.yaml`](examples/settings.yaml) holds every section with every key at its default, each key a comment with its description above it: applying it as it is sets nothing. Copy it, uncomment the keys you change and leave the rest out, so a default a later release changes still reaches them. `embry0 settings export --default` prints the same file; it is generated from the sections (`python -m embry0.settings.example --write docs/examples/settings.yaml`) and a test fails when it is out of date.

| Command | What it does |
|---|---|
| `embry0 settings check FILE` | Validates the file offline, with the checks a write meets, against the sections of the embry0 it runs from, and prints every problem as `key: message`, the words the API's 422 uses, never the value. Needs no orchestrator and no key, so it runs in CI. It cannot see what is stored, so what only a newer release knows, a section or a key of a known section, is reported here and kept by the orchestrator (see *After a rollback*) |
| `embry0 settings diff FILE` | A dry run through the API: whether the file would change the stored document, each key it changes (stored before and after, and the default a key falls back to), and the text diff. Stores nothing |
| `embry0 settings apply FILE [--reason TEXT] [--yes] [--allow-unset]` | Reads the stored generation, shows the diff against it, asks, then stores the file with source `file` and `If-Match` naming that generation, so a document someone changed in between is refused rather than overwritten. A file that is the stored text already sends nothing more and records no revision. Without a terminal it needs `--yes`. Each key that is set now and that the file leaves out is listed under *unsets*, since it goes back to its default; the prompt says how many, and `--yes` unsets them only with `--allow-unset` too. A reason is at most 500 characters |
| `embry0 settings set SECTION KEY=VALUE... [--reason TEXT] [--yes]` | Changes those keys of one section and leaves the rest of the stored document as it is, comments included. A value is JSON when it is JSON: `12` and `2.5` are numbers, `true` and `false` switches, `'["mon", "wed"]'` a list (quoted for your shell), and `KEY=null` takes the key out, back to its default. Anything else is text as written, such as `08-17` or `Europe/Berlin`, so `yes`, `~` or `0x10` is never another value: a section refuses text where it wants a number or a switch. A number written with a leading zero or a colon (`010`, `1:30`) is refused, since it could be meant as text: write `10`, or JSON text such as `'"09:30"'`. A list or mapping must be JSON. Like `apply` it reads the generation, shows what the change does against it, asks, then writes it with `If-Match` naming that generation (source `person`). Without a terminal it needs `--yes` |
| `embry0 settings export [-o FILE]` | Writes the stored document as written, comments included |
| `embry0 settings export --default [-o FILE]` | Writes the example: every key at its default, as comments. Offline |
| `embry0 settings import-env [-o FILE]` | Writes a document holding each policy variable this environment sets, by the rules of the import at startup: only a variable you set, whose value differs from its key's default and which the section accepts; a refused one is named on stderr and left out, and so is a name the import drops. A key whose variable is not set and whose value a deployment that existed before keeps (`leads.enabled`) is not in the file, since the environment alone cannot say; stderr says what the running deployment keeps and how to keep it in the file. Offline: it reads the environment and `./.env` it runs in, such as the orchestrator's (`docker exec embry0-orchestrator embry0 settings import-env`), whatever was imported before |
| `embry0 settings revisions [ID] [--limit N]` | Lists the changes, newest first (20 by default, up to 100), and names the one that can be undone; with an ID, that change with each key it changed and its text diff |
| `embry0 settings undo ID [--yes]` | Shows what undoing the newest change puts back, its keys and its text, asks, then undoes it (source `restore`) |

A file named `*.json` is read and sent as JSON, any other as YAML. `diff`, `apply`, `set`, `export`, `revisions` and `undo` read `EMBRY0_API_URL` and the API key (`EMBRY0_API_KEY`, `API_KEY`, then `./.env`), or `--api-url` and `--api-key`, like `embry0 onboard`. Writing needs an admin key without a repository allowlist, or for a repository's layer one whose allowlist covers it.

**A layer.** `--org OWNER` or `--repo PATH` (`group/name`, or `group/subgroup/name`) on `check`, `diff`, `apply`, `set`, `export` and `revisions` works on that organization's or repository's layer instead of the deployment's document (*Layers by organization and repository* above): `embry0 settings apply --org acme acme.yaml`. `check` then also refuses a key the layer may not set; whether its values combine with what the layer inherits needs the stored documents, which `diff` checks. `undo` takes the change's number, which names its layer. `import-env` and `export --default` are the deployment's only, and refuse `--org` and `--repo`.

The exit codes are the same for every verb, so a script can tell them apart:

| Exit | Meaning |
|---|---|
| `0` | Done: valid, applied, nothing to change, written, undone |
| `1` | Refused: the document has problems (a 422, or `check`), a variable `import-env` read is refused, or you answered no |
| `2` | Usage: a bad argument (a `KEY=VALUE` of `set` with no `=` or no value, a number with a leading zero or a colon, or a list or mapping that is not JSON), a file that cannot be read or written, `apply`, `set` or `undo` without a terminal and without `--yes`, or `apply --yes` that would unset a key without `--allow-unset` |
| `3` | Conflict: the document changed since it was read (409), or the change to undo is not the newest one, or no longer what is stored |
| `4` | Unavailable: the orchestrator cannot be reached, refused the key (401, 403), has no such revision (404), or failed |

**Kept in a file.** Write `managed_by: file` at the top of the document and the Policy tab shows it read-only, with how to change it: in the file, then `embry0 settings apply`; its history offers `embry0 settings undo` instead of an Undo button. Nothing else is refused: the API and MCP still write, so a change made there lasts until the file is applied again. A change of keys (`PATCH`, `embry0 settings set`, `settings_set_keys`) keeps `managed_by: file` and answers it, so the page or command that made it says so. To edit the document on the dashboard again, apply the file without `managed_by`. When a release moves a feature into the document, its first start imports your variables into the stored document, not into your file (*From the environment* above): startup then logs `settings_env_imported_into_file_document` naming each key it wrote, so copy those keys into the file, as the revision shows them. A key you do not copy is listed under *unsets* by the next `diff` or `apply` of the file, which puts it back to its default only once you confirm, or with `--allow-unset`. `managed_by` takes only `file`; turning it on or off is a change like any other, named `managed_by` in the history.

From an MCP client:

| MCP tool | Effect |
|---|---|
| `settings_get(owner="", repo="")` | The stored document: its text, its values, its `generation`, `settable` and `managed_by`; with `owner` or `repo`, that layer |
| `settings_effective(owner="", repo="")` | Every key's value in effect, its default and where it came from; with `owner` or `repo`, as that organization or repository reads it |
| `settings_schema()` | The JSON Schema of the document |
| `settings_set(text, expected_generation=None, dry_run=False, reason="", owner="", repo="", confirm=False)` | Replaces the whole document, or with `owner` or `repo` that layer. Pass the `generation` `settings_get` returned as `expected_generation`, so a change made in between is refused (409) rather than overwritten. A dry run needs no `confirm` and stores nothing; a write without `confirm=true` returns `confirmation_required` and changes nothing. A 422 names every bad key. Needs an admin key |
| `settings_set_keys(section, values, expected_generation=None, dry_run=False, reason="", owner="", repo="", confirm=False)` | Changes the keys of one section that `values` names, `{"remind_hours": 12}`, and leaves the rest of the document, or with `owner` or `repo` of that layer, as stored, comments included; null takes a key out. Checked, recorded and refused as `settings_set` is: `expected_generation` refuses a change made in between (409), a dry run needs no `confirm`, a write without it returns `confirmation_required`. Its answer's `managed_by` says when the document is kept in a file. Needs an admin key |
| `settings_revisions(revision_id=None, limit=20, owner="", repo="")` | The changes, newest first, of the document or with `owner` or `repo` of that layer; with `revision_id`, that change, of whichever document, with its text before and after |
| `settings_undo(revision_id, confirm=False)` | Undoes the newest change; without `confirm=true` it returns `confirmation_required` |

## Agent execution & auth modes

embry0 invokes Claude through a pluggable executor layer with two orthogonal config dimensions:

| Dimension | Values | Meaning |
|---|---|---|
| `execution_mode` | `sdk` (default), `cli` (Phase 2) | Agent SDK Python wrapper vs direct `claude -p` CLI subprocess |
| `auth_mode` | `oauth` (default), `api_key` | Claude Max OAuth token vs Anthropic API key |

All 4 combinations are valid in Phase 2+. **Phase 1 supports `sdk` only**; requesting `cli` at any level raises `ERR_INVALID_CONFIG` at resolve time.

### Five-level precedence

Later levels win:

1. **Global** — `Embry0Config.default_execution_mode`, `.default_auth_mode` (env vars `DEFAULT_EXECUTION_MODE`, `DEFAULT_AUTH_MODE`).
2. **Per-repo** — `repo_preferences.execution_mode`, `.auth_mode` columns.
3. **Per-job** — `JobCreateRequest.execution_mode_override`, `.auth_mode_override`.
4. **Per-agent-type** — `agent_definitions.execution_mode`, `.auth_mode` columns.
5. **Pipeline config (triage output)** — `pipeline_config.execution_modes[agent_type]`, `.auth_modes[agent_type]`.

NULL at any level falls through to the previous level.

### Credentials

- `auth_mode=oauth` requires `CLAUDE_CODE_OAUTH_TOKEN` in `.env` (generate one with `claude setup-token`). Missing token → `ERR_MISSING_OAUTH_TOKEN`.
- `auth_mode=api_key` requires an Anthropic `llm_api_key` account: one in the [credential registry](credentials.md) (dashboard: Infra → Credentials, bound at global scope or to the repo), or, when `DEFAULT_AUTH_MODE=api_key`, `ANTHROPIC_API_KEY` in `.env`. A repo, job or agent that switches to `api_key` while the deployment default is `oauth` needs the registry account. No account → `ERR_CREDENTIAL_MISSING`; an OAuth account resolved for an api-key run → `ERR_MISSING_API_KEY`.

The registry is consulted before the env vars; an OAuth token in `.env` is its last step.

### Safety policy (three rings)

1. **Container isolation** — ephemeral Docker sandbox, non-root, tmpfs workspace.
2. **Declarative permissions** — rendered into `/workspace/.claude/settings.json` per run (`permissions.allow` / `permissions.deny`). Enforced by Claude Code before tool dispatch.
3. **Programmable hook** — `evaluate_policy()` runs dangerous-Bash-pattern checks as a `PreToolUse` callable. Fail-closed.

Both execution modes consume the same `SafetyPolicy` data structure via different delivery mechanisms.

## CLI reference

### Production stack (`embry0`)

```bash
embry0 start              # Start the full stack
embry0 start --port 8201  # Start on a custom port
embry0 stop               # Stop the stack
embry0 build              # Build images (clean, no cache)
embry0 build --cached     # Build with Docker cache
embry0 build-sandbox      # Rebuild the sandbox and proxy images (prints the push step)
embry0 health             # Check stack health
embry0 config             # Validate and display config (secrets masked)
embry0 purge              # Remove all Docker artifacts
embry0 purge --volumes    # Remove only volumes
```

### Progression content pack (`embry0 progression-pack`)

```bash
embry0 progression-pack check my-pack.yaml     # Validate offline, every problem by key; exit 1 on one
embry0 progression-pack diff my-pack.yaml      # What applying it would change (a dry run)
embry0 progression-pack apply my-pack.yaml     # Show the diff, then activate it (--yes without a terminal)
embry0 progression-pack export --default       # The shipped default as YAML (-o FILE to write it)
```

Exit codes: 0 done, 1 refused, 2 usage, 3 conflict, 4 orchestrator unavailable, as for `embry0 settings`. See [progression.md](progression.md#from-the-command-line-and-mcp).

### Settings document (`embry0 settings`)

```bash
embry0 settings check settings.yaml     # Validate offline, every problem by key; exit 1 on one
embry0 settings diff settings.yaml      # What applying it would change (a dry run)
embry0 settings apply settings.yaml     # Show the diff, then store it (--yes without a terminal; --allow-unset to unset keys)
embry0 settings set asks remind_hours=12 # Change keys of one section, the rest as stored (KEY=null unsets)
embry0 settings export -o settings.yaml # The stored document, comments included
embry0 settings export --default        # Every key at its default, as comments (offline)
embry0 settings import-env              # A document of the policy variables this environment sets (offline)
embry0 settings revisions [ID]          # The changes, newest first; or one, with its diff
embry0 settings undo ID                 # Undo the newest change
```

Exit codes: 0 done, 1 refused, 2 usage, 3 conflict, 4 orchestrator unavailable. See [From a file, the command line and MCP](#from-a-file-the-command-line-and-mcp).
