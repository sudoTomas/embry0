# ADR 0028: Operator policy is layered by organization and repository; a section declares what each layer may set

Status: accepted (2026-10-29)

One deployment can serve several organizations, and their policy differs, so the settings document of [ADR 0026](0026-settings-document.md) is no longer the only place a value can come from. An organization and a repository can each have a layer: a document of the same shape, stored, validated, versioned and undone exactly as the deployment's, holding only what that organization or repository sets. A key takes the value of the most specific layer that sets it, deployment, then organization, then repository, and a layer replaces an inherited value whole, never merging into a list or an object. A layer may set only the keys its section declares for that level (`org_keys`, `repo_keys`); anything else is refused naming the key, so a section's author decides what is the deployment's alone. A repository belongs to the organization named by the first segment of its slug (ADR 0010), and work with no repository reads the deployment's values. Every loop reads every layer from one snapshot, checked with one query per tick, so reading per repository costs nothing per repository. A value that combines badly with what it inherits is refused when written; one that a later change below it makes do so is read as the inherited value with a warning, so a tick never fails on it. Writing a layer takes an admin; a repository's layer also takes an admin key whose repository allowlist covers it. New per-repository policy that has a deployment or organization default is a section key a layer may set, not a column of `repo_preferences`, which keeps facts about a repository with no wider default.

Evidence: migration 134; `embry0/settings/scope.py`, `embry0/settings/layers.py`, `embry0/settings/store.py`; `embry0/api/v1/settings.py`; `docs/superpowers/specs/2026-10-29-settings-layers-design.md`; issue #161.
