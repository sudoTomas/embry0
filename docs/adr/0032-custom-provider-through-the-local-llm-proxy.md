# ADR 0032: Every sandbox reaches its custom credential's server through the local-llm-proxy, enrolled with that server alone

Status: accepted (2026-11-25). Replaces the sentence of [ADR 0018](0018-openai-compatible-providers.md) that made a custom endpoint's host an egress exception, and the single upstream of [ADR 0023](0023-local-llm-proxy.md).

ADR 0023 left two routes to an operator's model server. With `LOCAL_LLM_UPSTREAM` set, every sandbox on the `custom` provider went through the local-llm-proxy to that one root with `LOCAL_LLM_API_KEY`, whatever its credential named. Without it, the credential's host was an egress exception for the job, which opens every port of the server's machine to code the job runs, with the server's key in the sandbox. The two variables configured the server a second time, two credentials scoped to different repositories could not reach different servers, and the orchestrator's own calls used the credential's address and key while the runs did not.

So a custom credential is its server: its address (`metadata.base_url`) and its key, as [ADR 0031](0031-provider-catalogue.md) already keeps addresses out of the catalogue. The local-llm-proxy always runs, configured with no server. The orchestrator enrolls each sandbox whose job resolved the `custom` provider with that credential's id, API root and key, the way the git-proxy scopes an enrolment to one repository, and the proxy forwards that sandbox to that server and no other, under the rules ADR 0023 set: two paths, the sandbox's bearer checked and dropped, the server's key added there, and a request body over `LOCAL_LLM_MAX_REQUEST_BYTES` refused with 413. A proxy that does not confirm the server it was given is refused, as an older git-proxy is. No sandbox is given a model server's host as an egress exception, and none is given its address or key; with no proxy running, or a credential that names no server, the job does not start. A resumed job's sandbox is enrolled again with the server its credential names then.

`LOCAL_LLM_UPSTREAM` and `LOCAL_LLM_API_KEY` route nothing. `embry0 credentials import-env` copies them once into the environment's custom credential (`custom/api-key`), with `CUSTOM_LLM_API_KEY` or a placeholder when no key was given, and leaves every stored custom credential as it was written. While either variable is set, startup says so. Since a stored credential may carry a placeholder address or key that the single upstream used to stand in for, startup also probes each stored custom credential once and names, in the log, one whose server cannot be reached or refuses its key.

Consequences: each credential reaches its own server, so a repository's binding picks the server per job, and its slots ([`local_model_leases`](../providers.md#local-models)) are that credential's. The orchestrator's own calls still reach the server directly, with the same address and key. A change under `embry0/execution/proxy/` needs the proxy image rebuilt, and the deployment must run the import before custom jobs reach a server the variables named.

Evidence: `embry0/execution/proxy/local_llm_proxy.py`; the enrolment in `embry0/execution/proxy/manager.py` and `embry0/execution/sandbox_manager.py`; `embry0/services/credentials/import_env.py`; `embry0/services/local_model_servers.py`; issue #174.
