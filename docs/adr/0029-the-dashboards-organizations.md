# ADR 0029: The dashboard's organizations are those its key's allowlist covers; everyone else reads the deployment's

Status: accepted (2026-11-09)

The `ui` section ([ADR 0026](0026-settings-document.md)) says whether the dashboard shows the game layer and which page it opens on. Its layers ([ADR 0028](0028-settings-layers.md)) need an organization to read for, and the dashboard's caller does not carry one: a session carries an email, a name and roles, and an API key at most a repository allowlist. So the caller's organizations are the ones its allowlist covers: the owner of each entry's current slug, `REPO_RENAMES` applied, as a repository's layer is found. A caller with an allowlist reads each of those organizations' layers over the deployment's document. It sees the game when any of them has it on, and opens on the page those with the game on agree on, else on the deployment's. A caller with no allowlist reads the deployment's values: every SSO session, the master key and every key without a list. Such a caller sees every organization's work, and no rule among several organizations' values would also keep the deployment's own setting a switch for its own people. An organization may therefore set `ui.game` and `ui.home`. A repository may set neither, since no caller is one repository's. One resolver (`embry0/api/v1/ui.py`) answers `GET /config/ui`, gates the game's routes and chooses the words of the Decisions page and of the cards a chat is handed, so what a caller is shown and what the API answers it never disagree. The value decides what an organization's people are shown, not what is counted: the game is one account whose characters are the deployment's agents. A key whose list covers several organizations sees the game on for all of their work once any of them has it on. The game itself does not filter by organization.

Evidence: `embry0/settings/sections/ui.py`, `embry0/api/v1/ui.py`, `tests/unit/api/test_ui_settings.py`; issue #177.
